# Кейс 08. Time Doctor — диагностика синхронизации времени

**Направление:** сетевое и системное администрирование  
**Целевая ОС:** Astra Linux Special Edition 1.8 x86-64  
**Команда:** 3 человека  
**Срок:** 1 семестр  
**Имя `.deb`-пакета:** `time-doctor`

## 1. Цель
Диагностика timezone, NTP/chrony, источников времени и качества синхронизации.

## 2. Итоговый продукт
Законченная программа, которая устанавливается из `.deb`, запускается штатно из системного PATH, имеет исходный код в GitFlic, тесты, CI и документацию. Нельзя сдавать только набор команд/скриптов без единого интерфейса, packaging и тестов.

## 3. Обязательный функционал
1. timezone и текущее состояние часов.
2. определение механизма синхронизации.
3. sources/selected source.
4. offset/stratum по доступным данным.
5. проверка доступности настроенных серверов.
6. экспорт отчёта без автоматического изменения времени.

## 4. Обязательные границы
- Работать только с ресурсами учебного стенда или явно разрешёнными в конфигурации.
- Не выполнять скрытые или разрушительные действия.
- Системные изменения — только после валидации; где применимо, нужен `dry-run`, backup и rollback.
- Не хранить секреты в Git.
- Не требовать root для операций чтения, которым root не нужен.
- Не считать отсутствие прав «неизвестной ошибкой»: приложение должно объяснить причину.

## 5. Приёмочные сценарии
- [ ] **A1.** sync/unsync различаются.
- [ ] **A2.** недоступный сервер виден.
- [ ] **A3.** отсутствие chrony обрабатывается.
- [ ] **A4.** отчёт содержит ключевые показатели.
- [ ] **A5.** работает в локальном NTP-стенде без Интернета.

## 6. Минимальный интерфейс
Обязательно должны работать:
```text
time-doctor --help
time-doctor --version
```
Также должна быть команда/действие основной функции кейса и, если применимо, команда `status`, `check` или `doctor`.

## 7. Тесты
Команда должна реализовать:
- unit tests для доменной логики;
- тесты валидации конфигурации;
- тесты нештатных входных данных;
- минимум один integration/smoke test на Astra Linux;
- минимум один отказной сценарий;
- финальную таблицу PASS/FAIL по acceptance.

## 8. `.deb`
Пакет `time-doctor` обязан:
- ставиться `sudo apt install ./dist/<file>.deb`;
- объявлять зависимости;
- класть executable в PATH;
- не содержать `.git`, IDE cache, dev venv и реальные секреты;
- корректно обновляться с предыдущей учебной версии;
- корректно удаляться;
- устанавливать systemd unit/timer только если это нужно архитектуре.

## 9. GitFlic CI
Минимальный pipeline:
```text
lint -> test -> package
```
Финальный pipeline основной ветки должен быть зелёным, а стадия `package` — создавать `.deb`.

1. Дополнительные функции реализуются только после завершения всего обязательного функционала кейса.

3. CI настраивается после того, как соответствующие команды проверки и сборки устойчиво выполняются локально.
4. Системно-зависимые операции должны проверяться на специально подготовленных объектах учебного стенда; использование внешних или неразрешённых ресурсов не допускается.
5. При выявлении дефекта команда возвращается к этапу, на котором возникла причина, вносит исправление и повторяет все затронутые проверки.
6. Завершённость проекта определяется воспроизводимостью результата, а не объёмом исходного кода или сложностью пользовательского интерфейса.


## 12. Защита
В `docs/demo.md` подготовить демонстрацию на 7–10 минут: проблема → архитектура → установка `.deb` → основной сценарий → один отказной сценарий → CI/tests → вклад каждого участника → ограничения.
